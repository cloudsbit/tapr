# Tapr中的高性能磁带流

作者：Klaus Birkelund JENSEN [1] 和 Brian VINTER

*Niels Bohr 研究所，哥本哈根大学，丹麦*

**摘要**：本文描述了 Tapr 高性能磁带流系统的设计与实现。Tapr 由多个基本进程组成，这些进程通过 CSP 风格的通信通道进行消息传递。该系统高度并发，使用同步和异步协调，而无需复杂地使用传统锁。通过将磁带库的每个部分表示为通信进程，系统可以扩展到当代企业级所谓的自动磁带库，甚至超越其规模。这包括机器人换带器、每个磁带驱动器、所有客户端，甚至加载的磁带介质。

我们展示了如何利用 Go 编程语言中的并发原语相对轻松地实现这样的系统。我们还描述了如何通过使用上下文的概念直接在语言中处理复杂的取消和超时处理。

最后，我们展示了一些基准测试，旨在表明通信进程架构不会引入任何可测量的开销，反而允许系统通过简单直观的基于进程的设计扩展到大量客户端和设备。

**关键词**：通信进程架构，数据流，高性能系统



## 引言

几十年来，磁带一直用于数据的长期归档，例如在 CERN，CASTOR [1] 系统使用磁带归档实验数据。磁带的核心技术没有太大变化，但 LTO 联盟推出了许多版本的线性磁带开放（LTO）技术 [2]。LTO 是 90 年代末开发的一个开放标准，得到了 IBM、HP 和 Quantum 等主要磁带供应商的支持。该标准描述了诸如外形尺寸、容量、每带的包裹数、每包裹的轨道数等特性。最新的标准 LTO-7 具有 6 TB 的原始数据容量 [3]，并包含近 1000 米的磁带织物。

虽然磁带、驱动器和必要的驱动程序通常可用，但操作这些设备所需的软件主要由专有产品和少数免费提供的开源产品主导；Bacula [4]、其分支 Barcos [5] 和 Amanda [6]。Bacula 和 Barcos 专注于差异和增量备份，不包括简单的归档功能。

专有产品通常更为先进，面向企业市场。其中最著名的是 IBM Spectrum Protect [7]（前身为 IBM Tivoli Storage Manager）和 Veritas NetBackup [8]。现有软件在纯归档使用方面的现状促使我们开发了一个新的竞争者 Tapr，本文将描述其设计和实现，以及软件的当前状态。



## 1. 背景

由于磁带媒体是顺序性的，因此存在一些挑战。最大的挑战是顺序性本身。为了在媒体上定位数据，必须进行代价高昂的搜索。通过媒体扫描所有数据因其物理特性而复杂。LTO-6 磁带由四个 846 米的带区组成，每个带区有 34 个“绕组”。带区包含在一个单独的线轴上，以蛇形方式书写。这意味着磁带必须进行 136 次端到端的传输才能填满磁带。每次磁带到达磁带的起点或终点时，它必须减速、停止，然后反向加速。全速下，LTO-6 磁带可以写入高达 160 MB/s。LTO 允许磁带以各种速度运行以匹配传入的数据速率，限制了旧磁带技术的所谓“擦鞋效应”。擦鞋效应发生在数据不能足够快地传递到驱动器时。当磁带在位置 A 处用完输入数据时，它必须停止并反向到某个位置 B < A。当数据准备好时，它必须从位置 B 加速，然后在到达位置 A 时开始写入。虽然 LTO 处理得更好，但驱动器和磁带在最高速度下运行效果最好。

保持磁带在最高速度需要特殊处理慢速写入，要么通过缓冲（或分段）大数据量在磁盘或内存中然后再冲刷到磁带。另一种更有效的方法是将多个写入器复用到同一磁带上，如果所有客户端的数据速率总和大于或等于驱动器的最大数据速率。

### 1.1 自动磁带库

自动化磁带库仍在许多企业和科学社区中使用，CERN 是一个显而易见的大规模例子。自动化磁带库由一个或多个自动更换器或机器人组成，这些机器人在存储槽和磁带驱动器之间移动媒体。作为一个单元看，自动化磁带库提供的带宽和并发性与单元中的驱动器数量直接相关——其次是自动更换器数量。

与磁带库的交互通过低级 SCSI 命令完成，每个驱动器在类 UNIX 操作系统中表示为一个设备文件。自动更换器通常表示为 /dev/changer 或另一个通用 SCSI 设备文件名。该设备用于查询库的库存并执行如将卷从存储槽转移到另一个槽的操作。在 Linux 和 UNIX 上，这通常通过使用媒体更换工具或 MTX 来完成。在 Tapr 中，我们直接使用这些工具来操作更换器，而不是使用错误且潜在危险的低级 SCSI 命令应用。

#### 1.2 存储

与磁带驱动器的交互也通过 SCSI 接口完成，在 Linux 和 UNIX 上，具体通过 st(4) SCSI 磁带驱动程序和 ioctl(2) 系统调用控制。驱动器表示为字符设备（不同于块设备的硬盘），可以像任何其他文件一样打开、写入或读取和关闭。传统上没有文件系统，但磁带支持文件标记。这些是磁带上的特殊标记，允许工具如 mt(1) 寻找到下一个或前一个文件或记录的开始。标准化的缺乏导致不同的磁带系统彼此不兼容，它们都在磁带上实现了自己的存储策略。磁带归档器 tar(1) 于 1979 年首次出现在 AT&T UNIX 第七版中，直到 1988 年才标准化，即使如此，不同操作系统中的 tar 归档格式也可能有微妙差异。

因为这些原因，我们选择使用 LTFS，线性磁带文件系统。LTFS 主要由 IBM 开发，并随着 LTO-5 磁带和驱动器引入，LTFS 由一个用户空间应用组成，允许磁带通过 FUSE 挂载为常规 POSIX 文件系统，带有目录和文件。文件系统是标准化的，所有主要 LTO 供应商提供的 LTFS 版本都针对其硬件进行了优化。因为磁带格式化为文件系统，它成为自描述的，使得所有存储的文件都可以轻松恢复，只要磁带可以在支持 LTFS 的系统上挂载。虽然使用 FUSE 引入了一些开销，但我们在磁带上达到最大数据速率时没有遇到任何问题。LTFS 使得处理磁带变得非常简单，因为它支持使用常规 POSIX 工具如 cp(1)、mv(1) 和 rm(1)。LTFS 的参考实现是开源的，可从 IBM 获得。在我们的情况下，我们使用 Oracle 修改的版本，因为我们的实验设置使用 Oracle 硬件。除了这个开源版本，主要供应商也有专有的库版，允许将整个自动化库视为一个大文件系统，随着用户遍历文件系统，卷自动加载和卸载。

#### 1.2.1 分区

LTFS 格式化卷分为两部分。第一个索引分区位于磁带的开头，保存文件和文件夹在磁带上的位置索引。这意味着卷可以挂载，并且内容快速列出，而无需扫描整个卷。这是一个优势，因为通过整个 LTO-7 磁带需要大约 100-110 秒。

第二个分区保存数据，只能追加。因此，文件删除或修改总是写入磁带末尾，只需更新索引。这隐含地使 LTFS 成为版本化文件系统，通过加载旧的索引，可以将磁带恢复到任何时间点。索引分区也是只追加的，因此它本质上作为写时复制数据结构。为了提高效率并限制由于过度搜索导致的磁带磨损，索引通常保存在内存中，并根据策略写入。当前的参考实现包括三种策略：基于时间的策略，每 n 分钟写入一次索引；每次关闭文件时写入索引的策略；以及仅在卸载文件系统时写入索引的策略。在 Tapr 中，我们出于效率原因使用卸载策略。注意，如果电源在磁带挂载时失败，可以使用工具 ltfscheck 扫描卷并更新索引。

## 2. 系统描述

为有效利用大规模磁带库进行长期数据流归档，有几个要求：

- 至少有两个驱动器专用于写入。这一要求源于磁带挂载/卸载的较长时间。在自动化库中，机器人首先必须从驱动器上卸载磁带并将其返回到存储槽。在此之前，磁带必须倒带并从驱动器中弹出。然后，必须找到新的“空白”卷，并通过机器人移动到驱动器。可以看出，这一过程会占用磁带上大量的时间。如果只有一个驱动器，则整个传输过程必须暂停，直到完成卷更换过程。通过增加驱动器数目，可以在一个驱动器上进行数据流写入的同时，在另一个驱动器上进行磁带更换，从而实现系统的并行操作和高效利用。

- 专用的读取驱动器。读取磁带的操作与写入操作不同，因为读取是顺序性的，且通常涉及搜索操作。这意味着读操作会影响写入操作的整体性能，尤其是在高数据流量的情况下。通过专用读取驱动器，读取操作可以独立于写入操作进行，从而不会影响写入的性能。

- 高效的缓存机制。为了保证磁带始终以最佳速度进行写入，必须提供足够的缓存，以缓冲传入的数据流。缓存可以是内存缓存或磁盘缓存，目的是确保数据流的稳定性和一致性，从而避免因数据传输速率波动而导致的磁带停顿和倒带操作。

- 智能的磁带管理策略。磁带库中的每卷磁带都有其生命周期，包括初次使用、读写操作频次、退役等。智能的磁带管理策略包括卷的自动选择和切换、磁带健康状态监测和预警、以及磁带的自动退役和更换。通过智能管理，可以最大限度地延长磁带的使用寿命，提高系统的整体可靠性和性能。

- 并发处理能力。为了应对大量并发数据流的需求，系统必须具备高并发处理能力。这意味着系统架构需要支持多线程或多进程操作，确保每个数据流的独立处理和传输。同时，系统需要具备高效的任务调度和资源分配机制，确保系统资源的最优利用。

## 3. 实现

为了实现上述要求，我们选择使用 Go 编程语言。这是因为 Go 语言内置了丰富的并发编程支持，尤其是 goroutine 和 channel 机制，使得并发编程更加简单和高效。系统架构采用 CSP（通信顺序进程）风格设计，所有组件通过消息传递进行通信和协调。

#### 组件设计

系统由多个独立的进程组成，包括：

- 客户端进程：负责接收用户的归档请求，并将数据流传输到服务器。
- 服务器进程：负责管理磁带库的资源，包括磁带驱动器、自动更换器等。服务器进程接收客户端的传输请求，并根据策略分配适当的资源进行处理。
- 磁带驱动器进程：负责具体的磁带读写操作。每个磁带驱动器由一个独立的进程管理，确保操作的并发和独立性。
- 缓存管理进程：负责数据缓存的管理和调度，确保数据流的连续性和一致性。
- 监控和管理进程：负责系统的状态监控、资源调度和异常处理等。

#### 并发控制

系统中各组件通过 Go 的 channel 进行通信。每个组件都是一个独立的 goroutine，通过 channel 发送和接收消息进行同步和协调。这种设计使得系统具有高度的并发性和扩展性，能够轻松应对大量并发请求。

为了处理复杂的取消和超时操作，我们使用了 Go 的 context 包。通过上下文机制，可以在整个调用链中传递取消和超时信号，确保资源的及时释放和系统的稳定运行。

### 基准测试

为了验证系统的性能，我们进行了多个基准测试。测试结果表明，基于通信进程架构的设计并不会带来显著的性能开销，反而通过简单直观的设计实现了系统的高效运行和扩展性。

以下是部分测试结果：
- 在并发100个客户端请求时，系统能够稳定处理并发数据流，磁带驱动器的利用率达到95%以上。
- 数据传输速率接近磁带的最大写入速率160 MB/s，且没有明显的停顿和倒带操作。

### 结论

本文描述了 Tapr 高性能磁带流传输系统的设计和实现。通过使用 Go 语言的并发原语和通信顺序进程架构，我们实现了一个高度并发和可扩展的系统，能够有效利用大规模磁带库进行长期数据流归档。系统的基准测试结果验证了设计的有效性和性能。

未来工作包括进一步优化缓存管理策略，提高系统的容错能力，以及增加对更多磁带格式和硬件的支持。
