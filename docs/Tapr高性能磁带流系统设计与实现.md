# `Tapr`中的高性能磁带流

作者：Klaus Birkelund JENSEN [1] 和 Brian VINTER

*Niels Bohr 研究所，哥本哈根大学，丹麦*



**摘要**：本文描述了 `Tapr` 高性能磁带流系统的设计与实现。`Tapr` 由多个基本进程组成，这些进程通过 CSP 风格的通信通道进行消息传递。该系统高度并发，使用同步和异步协调，而无需复杂地使用传统锁。通过将磁带库的每个部分表示为通信进程，系统可以扩展到当代企业级所谓的自动磁带库，甚至超越其规模。这包括机器人换带器、每个磁带驱动器、所有客户端，甚至加载的磁带介质。

我们展示了如何利用 Go 编程语言中的并发原语相对轻松地实现这样的系统。我们还描述了如何通过使用上下文的概念直接在语言中处理复杂的取消和超时处理。

最后，我们展示了一些基准测试，旨在表明通信进程架构不会引入任何可测量的开销，反而允许系统通过简单直观的基于进程的设计扩展到大量客户端和设备。

**关键词**：通信进程架构，数据流，高性能系统



## 引言

几十年来，磁带一直用于数据的长期归档，例如在 **CERN**，其**CASTOR [1]** 系统使用磁带归档实验数据。磁带的核心技术没有太大变化，但 **LTO** 联盟推出了许多版本的线性磁带开放（**LTO**）技术 [2]。**LTO** 是 90 年代末开发的一个开放标准，得到了 **IBM**、**HP** 和 **Quantum** 等主要磁带供应商的支持。该标准描述了诸如外形尺寸、容量、每带的包裹数、每包裹的轨道数等特性。最新的标准 **LTO-7** 具有 6 TB 的原始数据容量 [3]，并包含近 1000 米的磁带织物。

虽然磁带、驱动器和必要的驱动程序通常可用，但操作这些设备所需的软件主要由专有产品和少数免费提供的开源产品主导；Bacula [4]、其分支 Bareos [5] 和 Amanda [6]。Bacula 和 Bareos 专注于差异和增量备份，不包括简单的归档功能。

专有产品通常更为先进，面向企业市场。其中最著名的是 IBM Spectrum Protect [7]（前身为 IBM Tivoli Storage Manager）和 Veritas NetBackup [8]。现有软件在纯归档使用方面的现状促使我们开发了一个新的竞争者 `Tapr`，本文将描述其设计和实现，以及软件的当前状态。



## 1. 背景

由于磁带媒体是顺序性的，因此存在一些挑战。最大的挑战是顺序性本身。为了在媒体上定位数据，必须进行代价高昂的搜索。通过媒体扫描所有数据因其物理特性而复杂。**LTO-6** 磁带由四个 846 米的带区组成，每个带区有 34 个“绕组”。带区包含在一个单独的线轴上，以蛇形方式书写。这意味着磁带必须进行 136 次端到端的传输才能填满磁带。每次磁带到达磁带的起点或终点时，它必须减速、停止，然后反向加速。全速下，**LTO-6** 磁带可以写入高达 160 MB/s。**LTO** 允许磁带以各种速度运行以匹配传入的数据速率，限制了旧磁带技术的所谓“擦鞋效应”。擦鞋效应发生在数据不能足够快地传递到驱动器时。当磁带在位置 A 处用完输入数据时，它必须停止并反向到某个位置 B < A。当数据准备好时，它必须从位置 B 加速，然后在到达位置 A 时开始写入。虽然 **LTO** 处理得更好，但驱动器和磁带在最高速度下运行效果最好。

保持磁带在最高速度需要特殊处理慢速写入，要么通过缓冲（或分段）大数据量在磁盘或内存中然后再冲刷到磁带。另一种更有效的方法是将多个写入器复用到同一磁带上，如果所有客户端的数据速率总和大于或等于驱动器的最大数据速率。



### *1.1 自动磁带库*

自动磁带库仍然在许多企业和科学社区中使用，**CERN** 是最明显的大规模示例。自动磁带库由一个或多个自动换带器(*auto-changers*)或机器人(*robots*)组成，它们在存储槽和磁带驱动器之间移动磁带介质。当被视为一个整体时，自动磁带库提供的带宽和并发性直接与单元中的驱动器数量相关——并且在较小程度上与自动换带器的数量相关。

与磁带库的交互是通过低级别的 **SCSI** 命令完成的，每个驱动器在**UNIX -like**操作系统中表示为设备文件。自动换带器通常表示为 /dev/changer 或其他通用的 **SCSI** 设备文件名。该设备用于查询库的库存并执行诸如将卷从一个存储槽转移到另一个槽的操作。在 Linux 和 UNIX 上，这通常通过使用媒体换带工具(*Media Changer Tools* )或 **MTX** [10] 完成。在 `Tapr` 中，我们直接使用这些工具来操作换带器，而不是使用容易出错且可能危险的底层 **SCSI** 命令。



### *1.2. 存储*

与磁带驱动器的交互也是通过 **SCSI** 接口完成的，特别是在 Linux 和 UNIX 上通过 st(4) **SCSI** 磁带驱动程序并通过 ioctl(2) 系统调用进行控制。驱动器表示为字符设备（与作为块设备的硬盘驱动器不同），可以像任何其他文件一样打开、写入或读取和关闭。传统上没有文件系统，但磁带支持文件标记。这些是磁带上的特殊标记，允许像 mt(1) 这样的工具查找到下一个或上一个文件或记录的开头。这种缺乏标准化导致不同的磁带系统彼此不兼容，它们都在磁带上实现自己的存储策略。tar(1)，磁带归档器，最早出现在 1979 年的第 7 版 AT&T UNIX 中 [11]，直到 1988 年才标准化，即使在那时，不同操作系统在 tar 归档格式上也可能存在细微差异。

因此，我们选择使用 **LTFS**，即线性磁带文件系统 [12]。主要由 IBM 开发并随 **LTO-5** 磁带和驱动器引入，**LTFS** 由一个用户空间应用程序组成，允许通过 **FUSE** [13] 将磁带挂载为常规的 **POSIX** 文件系统，包括目录和文件。该文件系统是标准化的，所有主要的 **LTO** 供应商都提供了针对其硬件优化的 LTFS 版本。由于磁带格式化为文件系统，它变得自描述，因此如果磁带可以挂载到支持 **LTFS** 的系统上，所有存储的文件都可以轻松恢复。虽然使用 **FUSE** 引入了一些开销，但我们在达到磁带的最大数据速率方面没有遇到任何问题。**LTFS** 使得处理磁带变得更加简单，因为它支持使用常规的 **POSIX** 工具，如 cp(1)、mv(1) 和 rm(1)。LTFS 的参考实现是开源的，可以从 IBM 获得。在我们的案例中，我们使用 Oracle [14] 修改的版本，因为我们的实验设置使用 Oracle 硬件。除了这个开源版本外，主要供应商还有专有的*Library Editions* [15]，允许将整个自动库视为一个大文件系统，随着用户遍历文件系统，卷会自动加载和卸载。



### *1.2.1 分区*

**LTFS** 格式化的卷分为两部分。第一个 *index* 分区位于磁带的开头，保存文件和文件夹在磁带上的位置索引。这意味着可以挂载卷并快速列出内容，而无需扫描整个卷。这是一个优势，因为移动整个 **LTO-7** 磁带大约需要 100-110 秒 [16]。

第二个分区保存数据并且是仅追加的(append-only)。因此，文件删除或修改总是写入磁带的末尾，索引只是更新。这隐式地使 **LTFS** 成为一个版本化的文件系统，磁带可以通过加载较旧的索引恢复到任何时间点。索引分区也是仅追加的，因此它本质上充当写时复制数据结构。出于效率原因并限制由于过度查找而导致的磁带磨损，索引通常保存在内存中并根据策略写入。当前的参考实现包括三种策略：基于时间的策略，其中索引每 *n* 分钟写入一次；每次关闭文件时写入索引的策略；最后一种策略是仅在卸载文件系统时写入索引。在 ``Tapr` 中，我们出于效率原因使用卸载策略。请注意，如果在挂载磁带时电源故障，实用工具 ltfscheck 可以扫描卷并更新索引。



## 2. 系统描述

为了有效地将大规模磁带库用于数据流的长期归档，有一些要求。

- ***至少有两个驱动器专用于写入。** 这一要求源于磁带相对较长的挂载/卸载时间。在自动库中，机器人必须首先从驱动器卸载磁带并将其返回到其存储槽。在此之前，磁带还必须倒带并从驱动器中弹出。然后，必须找到一个新的所谓“空白”卷并将其从其存储槽移动到驱动器。然后，驱动器使磁带准备好写入。整个过程可能需要几分钟，但通过让另一个驱动器准备好空白卷来接管流，可以轻松隐藏这种延迟。这要求 `Tapr` 能够处理多个驱动器，以及一般的 *自动库*。
- ***足够的数据以保持驱动器高速运行。** **LTO** 驱动器能够控制挂载磁带的速度，但要保持最大带宽，系统必须能够向驱动器提供足够的数据。实现这一点的最简单方法是将多个流的写入交错。
- ***灾难恢复管理。** 作为一个长期归档系统，`Tapr` 应包括某种形式的灾难恢复。数据库可能会丢失，或者介质可能会在库中重新排列和重新定位。必须正确处理和管理这些不一致性。
- ***可扩展的客户端 API。** 由于 `Tapr` 旨在用作多种不同类型 I/O 系统的存储解决方案，系统的接口应易于扩展和适应其使用的任何环境。目前，我们仅实现了 HTTP/2 API，但该组件与服务器代码完全分离，因此可以轻松添加其他接口。另一个有价值的接口是类似于第 1.2 节中讨论的专有解决方案提供的 **FUSE** 层，它允许轻松浏览整个库中的文件。
- ***可扩展性。** `Tapr` 必须设计为高度可扩展和并发。它依赖于将磁带系统中的所有对象表示为通信进程。这包括媒体换带器、驱动器甚至卷本身。代码中没有暴露单个互斥锁，尽管底层运行时自然会使用它们。

这些要求使 `Tapr` 适用于许多环境，并且通过要求可扩展的基础，它允许系统管理当今由数百个磁带驱动器和数万个存储槽组成的库。图 1 显示了我们提出的总体设计。

在本节中，我们将讨论保持在理论抽象水平上。虽然 Go 经常在 CSP [17] 的背景下讨论，但它与 π 演算 [18] 有更多共同点，本讨论使用命名通道的概念以及通信进程。

`Tapr` 中的不同进程使用通道进行通信。通道以两种不同的方式使用。首先，通道用于通信，形式为请求，必要时带有回复。其次，它们用作实现流机制的手段，无需显式回复。通道是无缓冲的，在一个通道上进行通信需要一个准备好的发送者和接收者才能使进程继续。



### *2.1. 主要通信进程* 

设计包括三种主要类型的通信进程。它们的目的和基本行为如下所述。

**客户端(Clients)** 每个客户端都表示为一个进程。它负责从网络读取数据，将数据组装成特定大小的块，并将此块发送到驱动器以写入磁带。该进程还处理超时和取消，这将在本文的实现部分详细描述。

**驱动器(Drives)** 这种类型的进程包含单个驱动器的状态。客户端直接与其通信，通过将组装的数据块发送给它。驱动器进程处理媒体错误、卸载和加载媒体、将客户端从一个驱动器移动到另一个驱动器以及保持统计信息，如当前数据速率、连接的客户端数量等。它是系统中最复杂的进程，它用于处理媒体故障和客户端驱动器分配请求的机制将在实现部分详细描述。

**写入器(Writers)** 写入器进程是系统中最简单的进程。它仅执行基本通信，主要在两个数据通道上接收数据块并将其写入当前负责的介质。该进程透明地将多个写入流交错到单个磁带上，因为来自多个客户端的数据块按 **FIFO** 顺序到达通道。它有两个传入数据通道，因为一个通道专用于单驱动器写入，另一个通道专用于并行传输，其中多个写入器从这个单一的聚合一对多通道中获取要写入的块。

此外，通常会创建多个短期进程来执行异步操作，如统计更新和进程通信。这些是图 1 中所示的“系统和维护”支持进程的一部分。



### *2.2. 通信概述*

当客户端连接到服务器时，会创建 Stream 数据结构。流包含一个用于错误报告的专用通道和对数据通道的引用。数据通道指向流当前连接的驱动器的数据通道，或者如果正在执行并行或组写入，则指向特殊的聚合通道。每当客户端组装一个完整的块时，它就会在数据通道上发送，并期望在错误通道上收到回复。块直接进入写入器进程，而不涉及驱动器进程。如果写入器进程中没有错误，写入器会直接向客户端回复一个非错误值，表示成功。另一方面，如果在写入器进程写入时遇到错误，错误会发送到驱动器进程（而不是回复客户端），写入器进程立即终止。然后，驱动器可以选择如何处理错误。根据错误，这可能包括重试写入、将介质标记为故障或将流卸载到另一个驱动器，同时挂载一个新卷。在某些时候，当遇到错误时要写入的块将成功存储，另一个写入器进程将回复客户端的错误通道，表示成功，此时客户端将继续组装块并将其发送到新的写入器。如果由于某种原因无法写入块，驱动器进程可能会向客户端进程发送错误，然后客户端可以将错误作为响应发送并终止失败。

这种设计的好处是在执行成功时提供快速路径。还值得注意的是，由于主数据通道是在驱动器进程中分配的，而不是写入器，客户端将始终在合法通道上发送块。可能没有接收者，但通道永远不会关闭或以其他方式不可用。图-2显示了进程的基本关系以及它们在系统中的通信方式。

## 3. 实现

`Tapr` 是用 Go 编程语言 [19] 实现的。虽然不能说 Go 是为开发某些类型的系统而构建的，但 Go 包含的语言原语使得实现高度并发的系统变得容易。Go 还包括对编写支持 HTTP/1.1 [20] 和 HTTP/2 [21] 的服务器的良好支持。我们选择 HTTP 作为 `Tapr` 的初始接口，因为它可以从标准工具中使用，易于在 Go 中实现和使用，并提供 `Tapr` 所需的流机制。

Go 中的主要并发特性是 *goroutine*，一种轻量级的串行进程，原则上 Go 程序可以拥有几乎无限数量的 goroutine。这些进程没有传统的堆栈。goroutine 的堆栈在堆上分配，并根据需要增长和缩小，使其非常高效。

任何函数都可以通过简单地在函数调用前加上 go 关键字来作为 goroutine 启动。该函数将并发运行，控制权立即返回给调用函数。通道是使用内置函数 make 创建的。通道是类型化的，并且像语言中的其他所有内容一样进行垃圾回收。调用 make (chan int) 创建一个可用于发送和接收整数的通道。在 Go 中进行通道通信时，通常使用 go 关键字异步进行通信，例如通过调用 go func() { ch <- "message" }()。这样做时，问题就变成了如何取消该操作。如果在某个时刻通道的另一端没有接收者，该 goroutine 将永远留在内存中，直到程序终止。



### ***3.1. 超时和取消***

在 `Tapr` 源代码中有几个地方，进程必须调用 I/O 请求。一个例子是客户端获取驱动器。如果没有首选选择获取哪个驱动器，我们可以向每个驱动器发送获取请求。

在 Go 中，这是通过为每个驱动器进程调用单独的 goroutine（共享一个 *reply*-channel）来完成的。主进程（或周围进程）从 reply-channel 读取一次，一旦驱动器进程确认获取，单独的 goroutine 将在 reply-channel 上发送有关驱动器的信息。这种方法的一个问题是，如果没有为每个单独的 goroutine 完成读取，它们将泄漏并保留在内存中。一个天真的解决方案是启动 len(drives)-1 个 goroutine 来读取通道上的剩余消息，但我们真正想要的是能够向剩余的 goroutine 发出信号并让它们自行关闭。在通道上发出信号的常见方法是使用内置函数 close() 关闭它。这是因为在关闭的通道上接收将始终产生通道类型的零值。然而，不允许在关闭的通道上执行发送（或关闭）操作，这将导致 panic，除非显式处理，否则会崩溃程序。虽然可以从 panic 中恢复，但在这种情况下不应该这样做。在关闭的通道上发送几乎总是由于设计缺陷，Go 开发人员明确选择这种行为以促进良好的程序设计 [22]。由于这种行为，不可能在收到第一条消息后简单地关闭 reply-channel，因为这会导致发送 goroutine 中的 panic。

相反，引入了第二个通道，专门用于通过关闭它来发出操作完成或取消的信号，然后立即愿意传达通道类型的零值。用于通过关闭它发出信号的通道最好类型为 <-chan struct{}，这表示一个接收类型的空结构通道。使用空结构是因为它没有内存分配开销。无论使用多少，整个 Go 程序中只分配一个空结构。

这种模式在精心设计的 Go 程序中经常使用，以至于 Go 开发人员在 Go 1.7 版本中开发了 Context 包 [2]。该技术要求进程在多个通道上执行外部选择。在 Go 中，select 语句用于此目的。该语句在一组可以执行的发送和接收操作之间进行选择。如果多个操作准备就绪，它会伪随机地选择其中一个。



### *3.2. Context 包*

上下文是一种特殊类型，它在函数调用和进程之间传递截止时间、超时和取消信号。它还支持添加请求范围的值。Context 包只有 256 行代码，通过利用上一节讨论的相对简单的通道语义，实现了复杂的深度取消和超时处理。上下文值可以从其他上下文值派生，以形成一个树，其中取消上下文会导致所有派生的上下文也被取消。要正确使用上下文，必须在函数调用链中传播它。在 `Tapr` 的情况下，此链从接收 HTTP 请求的 HTTP 服务器开始。然后，根上下文由 context.Background() 函数创建。这个特殊的上下文不可取消，并且不携带截止时间或超时。如果客户端指定它需要独占访问磁带驱动器，它可以指定超时，以便在所有驱动器当前忙于服务其他客户端请求时不会永远等待。因此，通过调用 context.WithTimeout(rootctx, timeout) 从根上下文派生一个新上下文。该函数返回派生的上下文（现在携带超时）和一个取消函数，用于显式取消上下文。图 3 显示了派生上下文创建的树结构。

无论是否指定超时，上下文现在作为第一个参数传播到处理此请求的所有函数。在这种情况下，HTTP 服务器调用的第一个函数是 `Tapr` 中的 server.Store() 方法。到目前为止讨论的示例（获取驱动器）来自此函数。由于 Store() 将上下文作为第一个参数，因此它具有一个周围上下文。要正确使用上下文，每当函数具有上下文参数时，如果上下文被取消或超时，它应该通过提前返回来尊重它。通过选择上下文的 Done 通道来监视取消。清单 1 显示了如何使用 context 包。

![image-20250226090920266](assets\image-20250226090920266.png)

​                                                **图-3.** 派生上下文形成的树, 取消上下文将导致上下文及其所有派生（子）上下文的 Done 通道关闭



```go
func (s * Server ) Store ( ctx Context , ...) {
	derived , cancel := context . WithCancel (ctx)
	ch := make ( chan drive )
	for _, drv := range drives {
		go func ( drv * drive ) {
			if err := drv .Use ( derived ); err != nil {
				return
			}
			select {
				case <- derived . Done ():
				drv. Release () // we didn ’t need the drive anyway
				case ch <- drv :
			}
			}( drv)
	}
	select {
	case <-ctx . Done ():
		// timeout
	case drv := <-ch:
	cancel ()
	}
}
```

请注意，drv.Use() 函数也接受上下文参数。该函数不会简单地返回没有值，而是如果取消或驱动器不可用，则返回错误。使用派生的上下文，如果父上下文的超时隐式取消上下文，或者 Store() 函数显式调用 cancel()，则可能会发生这种情况。请注意，取消已经取消的上下文没有效果。
`Tapr` 中用于获取驱动器的代码比此处概述的代码稍微复杂一些。这是因为驱动器的选择并不像简单地选择第一个响应的驱动器那样直接。出于效率原因，我们希望选择一个能够充分利用带宽的驱动器，但如果另一个使用较少的设备也可用，我们不希望发送比设备可以处理的更多流。`Tapr` 还支持写入组，通过将流拆分到多个驱动器上提供并行写入，以及如果客户端要求数据以连续方式写入，则提供对驱动器的独占访问。



### *3.3. 流交错和并行写入*

高效使用磁带的一项关键技术是保持其以最高数据速率运行。在许多情况下，单个流不足以实现这一点。实现高持续数据速率的两种最突出的方法是暂存(staging)和流交错(stream interleaving)。流交错在 Veritas NetBackup [8] 中被大量使用。其要点是将多个流复用到同一介质上。如果有足够的数据速率可用，驱动器可以保持最大数据速率，同时仍然防止 *慢速写入器*。一个缺点是数据流被混合在一起，使检索复杂化。对于大多数长期归档场景，这很少是一个问题，正如我们将在第 3.3.1 节中看到的那样。

使用 IBM Spectrum Protect [7] 中使用的暂存方法，传入的流最初写入随机访问磁盘阵列，只有在有足够的数据可用以维持驱动器长时间运行时才刷新到磁带。这种方法的好处是允许软件重新排序并将数据共置在磁带上以获得更好的检索性能，但代价是需要一个昂贵的高性能磁盘阵列来处理传入的数据速率。

由于 `Tapr` 旨在处理要长期归档的高容量数据流，我们使用 *直接到磁带(direct-to-tape)* 技术，并积极进行流交错。数据通道的语义自动将数据块按 FIFO 顺序排队到磁带上。写入器进程不会尝试重新排序块。



### *3.3.1 流解复用*

当需要从磁带检索存档时，必须进行 *解复用(demultiplexing)*。在这里，必须从磁带中挑选出正确的存档块并重新组装成数据流。由于 `Tapr` 将始终按顺序写入流块，磁带永远不需要执行随机访问，但必须执行的前向查找次数与写入时活动的写入流数量直接相关。

![image-20250226091713814](assets\image-20250226091713814.png)

有两种方法可以实现这一点（见图 4）。一种天真的方法是简单地查找到块的开头位置，读取块，然后查找到下一个块。由于磁带驱动器无法被指示预取，驱动器将减速、查找，然后在读取块时加速。这种读取/查找循环将严重影响检索存档的数据速率，但影响程度取决于所选的块大小。如果块大小为几 GB，影响将不那么严重。

另一种方法通过顺序读取所有块并简单地丢弃不属于正在检索的存档的块来保持磁带以全数据速率运行。在这种方法中，块大小的选择不那么重要，因为驱动器不关心块边界。另一方面，在这种方法中，写入时活动的写入流数量直接影响感知带宽。



### *3.4 流分流和拆分*

单驱动器流交错使得检索数据相对容易，但如果传入数据速率超过单个驱动器的最大速率，客户端可以请求写入 *写入组*（见图 5）。目前，写入组在 `Tapr` 配置文件中静态定义。驱动器可以属于任意数量的写入组，目的是提供不同级别的并行性。如果客户端知道它将写入的数据速率，它可以请求独占访问并行写入组，并将传入的数据流透明地拆分到多个驱动器上，从而有效地倍增感知带宽。这使检索复杂化，因为如果不需要磁盘操作，现在必须由多个驱动器参与以正确顺序提取块。如果有暂存磁盘可用，可以从每个磁带依次提取块到磁盘，然后重新组装成数据流。应根据 `Tapr` 部署的环境和预期用途选择策略。如果检索很少发生，默认使用并行写入以获得更大的带宽可能是有益的。

![image-20250226091759840](assets\image-20250226091759840.png)

**图-5.** 当写入并行写入组时，流直接写入写入器接收的共享通道。当写入单个驱动器时，流与驱动器中分配的通道相关联，但不通过驱动器（用虚线表示）



由于 `Tapr` 被设计为用于科学实验原始数据的归档系统，它包含一个我们称为 *流分流* 的新功能，以 UNIX 工具 tee(1) 命名，该工具将标准输入复制到标准输出，同时在零个或多个文件中制作副本。该工具本身很可能以字母“T”命名，图形化地表示流分叉或拆分为两个。流分流用于将数据流引导到替代数据接收器，如分析引擎以进行即时消费。其想法是在数据流动时进行分析，如果可能的话，永远不要接触硬盘。分析结果可以引导回 `Tapr` 进行长期存储。



### *3.5. 流移交*

`Tapr`允许驱动器在流无法写入当前分配的驱动器时，将其移交给另一个驱动器。这最常发生在挂载的介质填满时，但也可能由于其他瞬态或永久性错误（如故障介质或驱动器）而发生。移交也可以通过直接请求驱动器来启动。如果服务器进程希望出于某种原因释放驱动器，则可以这样做。

在大多数情况下，如果有另一个驱动器准备就绪，流移交对客户端是透明的。如果没有，客户端将看到感知带宽下降。当写入器进程通知驱动器错误时，启动移交。如果错误与空间不足有关，则创建一个新的可取消上下文（无超时）。然后在单独的 goroutine 中执行获取另一个驱动器的代码。一旦获取到驱动器，goroutine 会在通道上发送驱动器。同时，启动一个 goroutine 来卸载 **LTFS** [12]，从驱动器中卸载介质并将其返回到存储槽，将新的空白卷加载到驱动器中，用 **LTFS** 格式化卷并最终挂载它。完成后，它通过发送一个新的写入器进程在通道上发出完成信号。启动两个 goroutine 后，驱动器进程进入 select 语句并等待其中一个完成。如果获取到另一个驱动器，则立即通过向获取的驱动器发送 Takeover 请求移交流。接管流的驱动器然后继续写入在填满的介质上未能写入的块，并继续透明地向客户端写入流中的块。如果没有另一个驱动器可用，卸载/卸载/加载/格式化/挂载过程最终将完成。此时，流继续在新介质上写入，之前创建的上下文被取消，以导致当前请求驱动器的 goroutine 终止。该过程如图 6 所示。
该过程表明，驱动器进程中的代码不关心它是由客户端还是另一个驱动器请求的。当由客户端请求时，上下文可能携带超时，如果需要将采取行动。当由另一个驱动器请求时，如果尚未终止，则仅显式取消。该过程还显示了使用上下文进行取消的通用性。

## **4.** **实验结果**

我们进行了多项实验，以衡量使用高度并发设计构建 `Tapr` 的影响。由于缺乏足够的 LTO 驱动器的实验设置，我们设计了实验以模拟写入磁带。具体来说，假设磁带以全速（160 MB/s）写入，在块大小为 64 MB 时，需要写入 400 毫秒。为了准确性，这不按比例缩小，因此写入器进程将为每个接收到的块睡眠 400 毫秒（或根据块大小不同的持续时间）。重要的是，数据仍然从网络读取并通过通道发送到写入器。

在所有实验中，假设有足够的数据保持驱动器全速运行，并且驱动器已经在全速运行。这样做是因为我们想衡量通信进程架构（和 Go 运行时）是否能够处理 10 千兆位链路上的传入数据。因此，我们还将实验限制在 8 个虚拟驱动器上，这等于 1280 MB/s（或 10 Gb/s）的聚合带宽。

我们的实验在 Dell PowerEdge R620 服务器上进行，配备两个四核 Intel Xeon E5-2603 v2 CPU，运行频率为 1.8 GHz，系统内存为 64 GB。系统运行 CentOS 6.7，内核版本为 2.6.32。`Tapr` 使用 Go 编译器版本 1.6 编译。

我们每次实验进行五次，并取平均值。



### *4.1. 写入吞吐量*

我们的前两个实验测量 `Tapr` 的写入吞吐量。实验在 1、2、4、16、32 和 64 个并发写入流下运行。首先，我们测量客户端请求其数据放置在单个驱动器上而不拆分到多个驱动器时的吞吐量。这是在有和没有块确认的情况下完成的，如第 2.2 节所述。客户端使用工具 curl(1) [23] 模拟，多个实例并行启动。

带宽是根据服务器处理整个请求的时间（从 HTTP 服务器接收到请求到向客户端发送响应）计算的。

表 1 显示了实验的原始结果。正如预期的那样，当客户端不需要对每个块进行确认时，我们实现了最高的吞吐量。在并发级别为 1、2、4 和 8 时，确认写入的吞吐量差异非常明显，确认写入将吞吐量降低到非确认写入的约 85%。然而，当并发流数量超过系统中的驱动器数量时，结果不确定。

目前，实现在等待确认时不会继续组装块，并且在缺少确认的情况下，只能组装一个块，同时等待将其发送到驱动器。这有利于限制内存消耗，但导致带宽利用率较低，如表 1 所示。

## 5. 结论和未来工作

在本文中，我们描述了 `Tapr` 的设计和实现，这是一个用于数据流长期归档的高度并发网络服务器。基本功能已经到位，但 `Tapr` 仍然是一个原型，尽管我们预计它将在哥本哈根大学投入生产，专门用于研究数据的长期归档。由于这种原型状态，仍然存在许多挑战以及未来工作的机会。

现代磁带系统提供的高带宽以及将流拆分以并行写入多个磁带设备的可能性可以有效地提供无限的带宽，仅受库中驱动器可用性的限制。这种水平扩展允许配置一个系统，可以处理大多数工业成像应用的带宽需求，而无需使用磁盘作为中间暂存区域。

我们在本文中的结果表明，虽然当许多流交错到驱动器上时，使用块确认的效果被摊销掉，但允许客户端继续从网络组装块并将其排队写入可能是有益的。虽然在 Go 中可以实现类似 CSP 的缓冲进程，但语言直接支持这一点；数据通道必须更改为具有特定大小的缓冲版本[3]。但正如结果显示，只要 `Tapr` 有足够的工作要做，这目前并不关键。我们注意到，这些结果是在模拟环境中完成的，因此虽然真实磁带驱动器的带宽可能会略有波动，但结果仍然表明 `Tapr` 设计能够处理 10 千兆位的数据流。在现实环境中，使用缓冲通道可能是有益的，设计仍然允许引入这一点。

虽然来自其他持久存储系统的数据写入在出现故障时可以轻松重试，但当数据从科学设备流式传输时，这是不可能的。为了更好地支持这一点，可以使用 TCP [24] 中使用的滑动窗口来限制块确认的数量，并限制重要数据的暂存需求。数据可以保留（或缓冲）在设备上，或直接存档在快速持久存储（固态磁盘或高性能磁盘阵列）上，直到数据已知写入持久（磁带）存储。

建议 `Tapr` 使用不同块大小的结果也提出了一个挑战。由于 `Tapr` 使用 **LTFS** 作为磁带上的文件系统，并且 **LTFS** 是一个常规的 **POSIX** 文件系统，当使用 4 MB 块时，6 TB 的 **LTO-7** 磁带在当前实现中将在一个目录中结束超过 150 万个文件。对于 64 MB 的块大小，这个数字仍然约为 100,000，因此在任何情况下，探索适当嵌套目录的方法可能是明智的。虽然这表明 `Tapr` 应该在磁带上使用自己的本机格式，但开放且受良好支持的标准的优势以及完全自描述的介质对 `Tapr` 的目标非常重要。目前，写入磁带的块的命名方案不容易支持嵌套结构，但我们相信这是可以解决的。

应该注意的是，我们并不后悔选择 Go 用于这个高性能应用程序。我们进行了相对较少的优化以实现最大吞吐量，唯一的优化是紧密的网络套接字读取循环和使用块池来限制垃圾收集器的压力。相反，我们广泛使用了 Go 中可用的并发功能来快速构建通信进程架构。虽然 CPU 使用率仍然相对较低，但很高兴知道 Go 会自动利用所有可用核心，因为随着更多设备添加到系统中，应用程序的并发级别会增加。
